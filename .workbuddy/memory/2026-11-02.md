## 修复：拖拽宠物绕圈不涨心情

### 根因（渲染层 src/windows/main/index.js `checkDragCircle`）
原实现每个 mousemove 事件都推进采样点，并要求「前后两段步长都 > 4px」才累加转角。
但拖拽时窗口跟手移动，鼠标相对屏幕虽然画圈，事件却极其密集（高刷屏每帧仅 1~3px），
两段步长永远达不到 4px → 转角累加恒为 0 → 整圈判定永远不成立。

数值模拟对比（阈值 0.8 圈）：

| 场景 | 旧算法 | 新算法 |
|---|---|---|
| 快画一圈 1500px/s 60Hz | 0.98 触发 | 0.98 触发 |
| 慢画一圈 300px/s 120Hz | **0.00 不触发** | 0.99 触发 |
| 很慢 120px/s 120Hz | **0.00 不触发** | 1.00 触发 |
| 165Hz 高刷 | **0.00 不触发** | 1.00 触发 |
| 小圈 直径200 | **0.00 不触发** | 0.99 触发 |
| 直线拖拽 / 来回抖动 | 0.00 / 0.50 不触发 | 0.00 / 0.50 不触发 |

### 修法
1. 改为**距离重采样**：位移不足 6px 就原地返回，采样点不推进；攒够 6px 才取下一个点。
   这样无论鼠标快慢，参与计算的相邻步长稳定 ≥6px，转角能正确累加。
2. 阈值 0.9 圈 → 0.8 圈，冷却 4s → 3s。
3. 主进程 `main.js` circle 分支：
   - 原来 `+getPetInfoOne("mood","info")` 为空时会算出 NaN 写进存档，改为 `|| 0` 兜底。
   - 去掉对 health 的硬依赖，改为 `_now < _max` 判断，心情满时跳过。
   - `openSpeak` 包 try/catch；`nextActiveStr` 由 "play" 改 "speak"（与 roller 分支一致，路径已验证）。
   - 加 `/tmp/qqpet-circle.log` 日志（用 `_require("fs")`，webpack 打包的代码不能用裸 require）。

### 经验
- **webpack 打包后的代码里不能用裸 `require(...)`**，必须用项目顶部的 `_require = eval("require")`。
- 路径曲率判定这类算法，**必须做距离重采样**，不能直接按事件采样再过滤短步长，
  否则在高采样率设备上（触控板/高刷屏）会完全失效。
- 验证这类算法用 Node 数值模拟比拼装 Electron 探针快得多，也更能列出边界场景。

## 修复：默认状态 ↔ 玩耍动画切换时白屏

### 根因（`src/windows/util/pet/swfPet.js` 的 `changeSwf`）
换片不是复用实例，而是 `cloneNode` 出一个新节点、appendChild 挂上，让 Ruffle 重新
初始化一个播放器实例并重新加载 SWF。而原流程是：
1. 旧节点 `style.opacity = 0`；
2. 90ms 后 `old.remove()`；
3. 新实例这时往往还没出首帧（WASM 初始化 + 读 SWF + 解码首帧远不止 90ms）。

中间那段「旧画面没了、新画面还没出来」就是白屏。

另外 `old.style.transition = "all 0.08s !important"` 是**非法值**（内联样式不接受
`!important`），CSSOM 直接丢弃，过渡从来没生效过，所以旧节点是瞬间消失，闪得更明显。

### 修法
- 旧节点不再设 `opacity = 0`，保持不透明盖在新节点上面；
- 新节点在下面静默加载；
- 新增 `fadeOutOld(old, neo)`：轮询新节点是否就绪（`neo.ruffle(1).metadata`，退化看
  shadowRoot 里的 canvas 是否有尺寸），就绪后再把旧节点 `opacity 0.12s` 淡出、150ms 后移除；
  800ms 超时兜底强制切换；
- 旧节点 `removeAttribute("id")`，避免和新节点同 id 时 `getElementById` 命中旧节点
  （原代码靠「先 remove 旧节点再 bindDom」规避，现在不能先 remove 了）；
- 换片前清理 opacity 已为 0 的残留节点，防止连续快速换片时节点层层叠加。

### 关键认知
用户指出「切换前后那一帧本来就应该是完全一样的」，所以交叉淡化在视觉上无感——
因为两张图内容相同，淡入淡出看不出过渡，只是把中间的白屏窗口补上了。

### 第一版修完仍闪白 → 真正的坑
**Ruffle 的 polyfill 会把挂上去的 `<embed>` 整个替换成自己的元素**，我们 clone 出来
的那个引用随即便脱离文档。第一版对它设 `opacity: 0` / `opacity: 1` 全都不生效，
真正在显示的替换节点从未被隐藏过，一露出来就是白底。

第二版修正：
1. 隐藏/显示一律通过 `document.getElementById(this.id)` **每帧重新取当前真实节点**，
   不对 clone 引用操作；
2. 换片一开始（appendChild 之后立即）就启动监视器，每 16ms 压一次透明度，
   消灭原来 90ms 的空窗；
3. 就绪判据用适配层现成的 `ffInstance()`（`node.instance` 优先、`node.ruffle(1)` 兜底），
   看 `current_frame() > 0` 或 `metadata`，并且至少等 `MIN_WAIT=220ms`（首帧渲染时间）；
   最长 `MAX_WAIT=900ms` 强制切换；
4. 交换方式改为**同一帧内瞬时交换**（新节点 opacity 1 + 旧节点 opacity 0，都不带 transition），
   因为两帧内容相同，瞬间切换完全看不出接缝；淡出反而会让两张图重叠 0.1s；
5. 清理残留节点时只处理 `EMBED` / 含 `RUFFLE` 的标签，否则会把 `.focusPress` 那层一起删掉；
6. 加 `_fadeId` 令牌：新一轮换片让上一轮的监视器立刻失效，否则旧监视器会按 id 摸到新节点、
   把刚显示的画面又压回透明。

### 经验
- 判断第三方 polyfill 元素的可见性/状态，**绝不能持有它插入前的引用**——polyfill 很可能会
  把节点整只换掉。一律按 id / querySelector 现取。
- `metadata` 类"元信息就绪"信号不等于"画面已渲染"，做视觉切换时要用更接近渲染的信号
  （帧号、presented 事件），并留一个最小渲染时间兜底。

### 经验
- 凡是和鼠标位移相关的判断，只要窗口会在拖拽时跟随移动，就必须用 screen 坐标而不是 client 坐标。
  同一份代码里 `checkDragCircle` 已经因为 clientX 失真改用 screenX 了，`petClick` 的判断漏掉了。
- 排查「改了没生效」时，先确认跑的是哪份代码（app.asar 时间戳 + grep 新符号），
  比在算法里反复找 bug 快得多。

## 修复：默认状态 ↔ 玩耍动画切换时「闪一下」（白屏）

### 定位手段（关键经验）
沙箱里跑不了带 GPU 的 Electron，`capturePage` 在 offscreen 窗口里还会返回**滞后帧**
（实测 ~80ms 才更新一次），拿来测 60~90ms 的空档会漏判。
改用「渲染层自己逐帧采样」才准：
- 每帧读 `getComputedStyle(node).opacity`、`getBoundingClientRect()`
- 直接 `getImageData` / `drawImage(canvas→24x24 探针canvas)` 数不透明像素
注意：`ELECTRON_RUN_AS_NODE=1` 在这个环境里是默认值，必须 `env -u ELECTRON_RUN_AS_NODE` 才跑得出主进程。

### 实测数据（真实 Ruffle + 真实 SWF）
| 指标 | 耗时 |
|---|---|
| 新实例挂载 → `readyState>=2` / `metadata` 就绪 | **~250ms** |
| 新实例挂载 → canvas 真正出现像素（首帧） | **~310ms**（缓存热后 100~130ms） |
| 原实现撤掉旧节点的时刻 | **90ms** |
| 我上一版撤掉的时刻（MIN_WAIT 220 / metadata 判据） | ~220~250ms |
结论：中间那 60~220ms 屏幕上**新旧都没有像素** → 透明窗口露出桌面 → 就是「闪白」。

### 修法（src/windows/util/pet/swfPet.js）
1. 新节点 `insertBefore` 到旧节点**下面**，加载期间被完全遮住；旧节点不透明继续演。
2. 就绪判据换成**读 canvas 像素**（`hasPaint`）：`getContext("2d")` 非空时用
   `drawImage(canvas, 0,0,24,24)` + `getImageData` 数 alpha>8 的采样点，≥6 个算已出画。
   `metadata`/`readyState` 比首帧早约 60ms，**不能**当判据。
3. 出画后同一帧把旧节点 `opacity:0`（用 `style.setProperty(..., "important")`，
   否则斗不过 index.css 里 `#pet { transition: all 0.08s !important }` 那条），120ms 后移除。
4. WebGL 渲染器读不到像素时（`getContext("2d")===null`）退回：
   `readyState>=2 && elapsed>=420` 再额外等 160ms 才交接 —— 旧节点在上层，多等只会「切换稍慢」，不会露白。
5. 旧节点让出 id 会同时失去 `#pet` 的 `width/height:100%、position、z-index`，
   元素会按 `<embed>` 属性尺寸重排（视觉上是宠物「跳」一下）。
   必须在 `removeAttribute("id")` 之前把 `getBoundingClientRect()` 的宽高固化成内联样式。

### 验证（无头 Electron 逐帧采样，4 个场景）
Stand→Speak、Speak→play、play→Stand、模拟 WebGL 兜底：
每场景 ~96 帧，**空帧 0、几何跳变 0**；可读像素时切换在 ~110ms 完成。

## 修复：「切换时出现 4 只手 / 动画重合」（重影）

### 根因
上一版为了不白屏，让旧节点一直演到新节点出画，同一时刻文档里存在两个 Ruffle 实例。
只要某个时刻两者的可见状态同时为真，就会叠成两只宠物。
更隐蔽的放大器：`this.dom` 会在换片 90ms 后被 `bindDom` 指向**还在下层加载的新节点**，
下一轮换片拿它当「当前画面」，就把真正的旧画面当残渣删掉，剩下的两个节点都没人负责隐藏。

### 修法：快照交接（`src/windows/util/pet/swfPet.js`）
任何时刻文档里最多只有一个 Ruffle 实例：
1. `freeze(node)`：把当前 canvas `drawImage` 到一张 `canvas.petFreeze`，
   先缩 24x24 采样确认非空白（≥6 点 alpha>8）才采用，内联 `z-index:10 / 100%` 盖在最上层；
2. 插入快照后**立刻 `old.remove()`** —— 旧实例当场销毁，不可能再参与渲染；
3. 新节点插在原位，`hideNode()` = `opacity:0 + visibility:hidden`（visibility 连溢出边缘一起挡掉）；
4. `revealWhenReady` 读到像素后才 `visibility:visible`，同帧 `dropSnap()`。
5. 新增 `showing / pending / frozen` 三个字段：换片基准永远是 `showing`；
   `curShowing()` 发现「带 id 的节点其实是 pending」时返回 null，让 `changeSwf` 把请求挂进
   `saveChange`，等这次交接完成后再重放（避免克隆出一个还没出画的空壳）。
6. 快照失败（WebGL 读不回像素）退回旧路线：旧节点继续演、新节点藏在下层。

### 验证（无头 Electron 逐帧采样，5 场景 / 约 1100 帧）
| 场景 | 同时可见最大 | 重影帧 | 白屏帧 | 空白快照 |
|---|---|---|---|---|
| 正常 1.5s | 1 | 0 | 0 | 0 |
| 400ms 连换 | 1 | 0 | 0 | 0 |
| 150ms 连换 | 1 | 0 | 0 | 0 |
| 60ms 抖 8 次 | 1 | 0 | 0 | 0 |
| 40ms（changeIng 窗口） | 1 | 0 | 0 | 0 |

负向对照（拆掉 hideNode + freeze）：**同时可见最大 3，重影帧 61/154** —— 证明探针有区分力。
快照约 8 帧（~130ms）后撤掉；最差快照有 83/576 个不透明采样点，不是空白图。

### 副作用（需知悉）
切换瞬间旧动画会**定格一帧**约 100~300ms，而不是继续演到新动画出画。
这是「保证只有一个实例」的代价；比白屏或重影都好，但如果用户觉得顿，可改回「旧节点继续演 + 每帧守卫」。

## 修复：切到站立时还会看到一点玩耍动画

### 根因（两层）
1. 快照是「冻结当前画面」，而当前画面正是**要离开的玩耍动画**。
   即使只停留 100~130ms，视觉上也是「站立之前又闪了一下玩耍」。
2. 「有时候有、有时候没有」= `freeze()` 抓当前帧**成败不稳定**：
   真机有 GPU 时 Ruffle 走 **WebGL 渲染器**，`preserveDrawingBuffer` 默认关闭，
   在 rAF 之外 `drawImage(canvas)` 经常读回空白 → `freeze` 返回 null → 退回兜底路径
   （旧节点继续演），于是看到的是「真的又播了一点」。无头探针因为 `disable-gpu`
   一直是 canvas 渲染器，所以测不出这个差异。

### 修法
1. **`src/windows/app.html`**：`preferredRenderer: "canvas"`。
   宠物尺寸小，canvas 渲染器性能足够；换来像素读回稳定，
   `hasPaint`/`freeze` 不再退化成「保守多等 400ms」的兜底分支。
2. **`src/windows/util/pet/swfPet.js`**：静态动作帧缓存。
   - `isStill(src)`：按路径含 `Stand` 判定（Stand 只有 1 帧，静态）；
   - `saveFrame(src, live)`：swap 成功时把该帧存进 `_frames[src]`；
   - `cachedFrame(src)`：换片时优先用它当快照 → **屏幕上立刻是目标姿势**，
     不再显示上一段动画；
   - 没有缓存（首次）才退回 `freeze(old)` 冻结当前画面；
   - `freeze` 重构出 `snapFromCanvas()`：校验非空白（24x24 采样 ≥6 点 alpha>8）+ 复制 + 摆位。
   - 动态动作不缓存（缓存的是上次播到的中间帧，会跳帧）。
   宠物长大后 swf 路径变化（GG/Adult…），缓存按 src 分 key，不会显示旧形态。

### 验证（切换前后画面指纹差异，16x16 RGBA 平均绝对差）
| 指标 | 值 |
|---|---|
| 切换瞬间快照 vs 站姿画面 | **0.7**（几乎完全一致）|
| 切换瞬间快照 vs 刚才的玩耍画面 | **34**（完全不同）|
| 快照就位耗时 | 20~25ms |

说明切到站立时屏幕上立刻就是站姿，没有玩耍残影。
高频连切（100ms × 8）与两次 play→Stand：**重影帧 0、白屏帧 0、空白快照 0**。

### 结论（用户已实测确认 ✅）
「站立↔玩耍切换」这条线彻底收口。三条不可回退的约束：
1. 任何时刻文档里**最多一个 Ruffle 实例**（快照交接，不做新旧并存）；
2. 「已出画」的判据只能是**读 canvas 像素**，`metadata` / `readyState` 早约 60ms，不能用；
3. app.html 固定 `preferredRenderer: "canvas"`，否则 GPU 下走 WebGL 读不回像素，
   抓帧时灵时不灵 —— 这正是「有时候有有时候没有」的来源。

## 修复：信息栏「领取」按钮时好时坏（灰 / 可点）

### 现象
打开信息栏，领取按钮是灰的（`.giftDisabled`），但打开任务栏能看到可领取的在线礼物。
用户自己猜到了关键：「是不是只有当前点开过任务栏，上面才会同步」—— 猜对了。

### 根因（懒生成 + 不信任的缓存）
礼物列表**不是常驻数据**，是 `Goods.getGiftData(type, n)` 懒生成的：
- `getGiftData` 全项目只有两个调用点：`getConsumablesPage({value:"task"})`（打开任务栏）
  和 `word.js` 的 gift 台词。**信息栏从来没调用它**，只读缓存。
- 缓存初值是 `pet.js` 的 `cache.gift = { sign: [], online: [] }`（空数组）。
- 所以两种情况必然出错：
  ① 首次跑（或 `$Store` 里没有 cache）→ 空数组，`for...of` 一次都不进 → claimable=0 → 灰；
  ② 跨过 06:00 进新一天 → 缓存还是昨天的列表、`isTake` 全是 2（已领），
     而在线礼的重置判据是 `nextTime` 距今 ≥864e5，只在 `getGiftData` 被调用时才触发 →
     不打开任务栏就一直读到「全已领」→ 灰。
- 打开一次任务栏后 `getGiftData` 生成/重置了列表，信息栏立刻正常 → 表现为「时好时坏」。

### 修法
`src/windows/popups/stateInfo/main.js` 新增 `calcClaimable()`：
先自己调 `petControl.Goods.getGiftData("sign",12)` / `("online",8)` 把数据补齐，再扫缓存。
两处内联判定（`load` 下发、`pet` 监听）都改成调这个方法。
数量必须与任务栏一致（12 / 8），否则 `getGiftData` 会因长度不符整份重新生成。

### 验证（用真实 Goods.getGiftData 跑对照）
| 场景 | 旧 | 新 |
|---|---|---|
| 首次启动、缓存为空、在线 130 分钟 | 灰 | 可领 |
| 首次启动、缓存为空、在线 5 分钟（只有签到礼） | 灰 | 可领 |
| 隔天首次打开、缓存全是昨天的已领、在线 130 分钟 | 灰 | 可领 |
| 隔天首次打开、在线 25 分钟（只够第 1 个） | 灰 | 可领 |
生成结果：签到 12 条、在线 8 条，在线 `time` = 10/40/70/100…分钟，`isTake` 全部 0。

### 附带确认
信息栏的「领取」是**直接领取**（走 `stateInfo_bus-openActive` → `toAddGoods`），
不是打开任务栏，所以不需要 `useType`。

## 优化：日常三类消耗品按新增属性值从小到大排序

### 属性来源（查了 shop.js 的真实字段）
| 分类 | type | 排序主键 | 说明 |
|---|---|---|---|
| 食物 | food | `starve` | 次键 = charm+intel+strong |
| 清洁 | commodity | `clean` | 次键同上 |
| 吃药 | medicine | `price` | 22 种药中 21 种 starve/clean/charm/intel/strong **全是 0** |

药品没有数值属性，只有 `desc`（用于治疗感冒…）；`price` 恰好对应病症轻重：
50 感冒 / 80 重感冒 / 120 肺炎 / 200 肺结核 / 240 百草丹 / 400 还魂丹。
唯一有属性的是 `_60001 还魂丹`（starve 500 / clean 500 / strong 100 / price 400），
按价格排也正好落在最后，不用特判。

### 实现要点
`src/windows/util/pet/Goods.js`
- 新增 `consumableSortKey(key, type)` → `[主属性, 次属性]`、`consumableCompare(type)`。
- 在 `getConsumablesPage` 里 **`r = r[o]` 之后、分页 slice 之前** 排序。
  放在 slice 之后只会排当前这一页，翻页仍然是乱的。
- **必须 `r.slice().sort()`**：`r` 是 `storeGoods[type]` 的数组引用（`getCache("store")` 的
  真实缓存），原地排序等于改了存档里的背包顺序。
- 条件 `"store" == a && !i && Array.isArray(r) && (o 是三类之一)`：
  排除商店（getWhere==="shop"）、排除礼物（useType 非空，礼物走 type_Key 结构）。
- 键解析兼容两种写法：`"food*_10013006-2"` 和 `"_10013006-2"`，取 `split("*").pop().split("-")[0]`。
  注意 shop 的键**带前导下划线**（`_10013006`），不能剥掉。
